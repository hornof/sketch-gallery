# Repo rules (apb)
## Who does what
- **Orchestrator** — the main Claude Code session, the one the human talks to. It drafts the PRD and TDD, keeps the board, and runs the build loop: take the top issue → spawn the builder on it → when the PR is open, spawn the reviewer → hand the PR to the human → after the merge, check the live product. It does not write feature code itself and never merges.
- **Builder** — a subagent the orchestrator spawns (`agents/builder.md` in the apb plugin). Writes the tests, then the code, opens one flat PR. Starts with no memory of the chat.
- **Reviewer** — a subagent the orchestrator spawns in a fresh context (`agents/reviewer.md`). Reviews the PR and the live product; writes no code.
- **Advisor** — optional; a Claude session outside the repo (Cowork) with broad access: thinking through the idea, research, independent reads. Never writes to the repo; its input is a comment on the relevant issue.
- **Human** — approves the three gates and merges.
## Rules
- Tests before code; one feature per flat PR off freshly-fetched main; never stack branches or push to a merged branch.
- Only humans merge. The reviewer is a separate session; it writes no code.
- After every merge, check the live product (the site, the published package, the released app), not just CI.
- The Projects board is the single progress tracker. Every PR and every commit names its issue (`#N`), so each change can be traced from the issue and back.
- When something goes wrong, add a rule here the same day.
- Approved PRD/TDD wording is immutable except by the human's explicit choice.
- Permissions: sessions run in auto mode (set in each human's `~/.claude/settings.json`; never put `defaultMode` in a repo file). At session start the orchestrator confirms the mode is auto (desktop: `get_session` "self"); if not, it tells the human in one line before anything else. One plain command per shell call: no `$(…)`, loops or `curl | grep` chains. Use WebFetch for web pages and a script file for multi-step logic. Every instruction to a builder, reviewer or research Claude repeats this command rule, since their permission prompts reach the human too. If a permission prompt appears mid-session, add the missing rule to `.claude/settings.json` the same day.
- `LOG.md` is append-only. A question for a human or the advisor goes on the issue — nothing important lives only in chat.
- Working with the human: follow the sections "How the human reviews" and "Helping the human keep track" in the playbook (`docs/playbook.md` in the apb plugin). In short: one question at a time, in plain chat; a merge or a clear yes is approval, but praise that comes with open questions is not; at a gate, get the yes before the merge, so the post-approval updates go into the same PR; show everything visual; one link per thing.
- When you add a new piece (a Claude artifact, a repo file, a folder, a scheduled task, an outside account), add it to `docs/MAP.md` at the same time.
- Keep the map current without being asked. After every merge, whenever a PR opens, at the end of each stage, and whenever the human asks where things stand: check every row of `docs/MAP.md` against the real state (GitHub, Claude artifacts, the human's computer, outside services) and fix it before replying. Check the board the same way: every issue in the right column, and an issue for the stage we are in. For things that change often, like PR or issue status, link GitHub's live list instead of copying the status.
- The map artifact is built from `docs/MAP.md`. After every change to `docs/MAP.md`, and again from main after each merge, run `python3 scripts/map-artifact.py <output.html> https://claude.ai/artifact/Pm6QZUibPcqXohWUKnVLSx`, then publish `<output.html>` to that same artifact link. Never edit the artifact by hand. Links to repo files point at the branch it was built from.
- Every PR gets a review from the reviewer agent, whether it holds code or only docs. The reviewer reads `docs/reviewer-notes.md` first and checks the code, one name per thing across files, the PR description, issues, the board and artifacts, whether every statement and link is right, and plain concise writing. It posts the whole review on the PR, in the format `docs/reviewer-notes.md` describes. The human rules on each item before anything is fixed. The orchestrator then fixes what the human approved, and adds each override or new rule to `docs/reviewer-notes.md`.
- After each stage, add an entry to `docs/HISTORY.md`: the stage's decisions, surprises and changes of mind.
- Before showing the human a markdown doc, check how GitHub displays it: `gh api markdown -F mode=gfm -F text=@<file>`.
- In a public repo, never name anyone who isn't on the repo.
- Claude Code works on GitHub as its own account, `hornof-claude`. Its token lives only in `.claude/settings.local.json`, never in a committed file. The orchestrator, builders and reviewers share that one account, so end every PR description and comment Claude writes with its role, for example `— Claude (orchestrator)`.
- Problems with the apb process itself go on hornof/apb as one issue per problem, labeled `from-sketch-gallery`.
- While an agent runs or a PR waits on the human or GitHub, apb's watcher runs (playbook, "While Claude waits"). The plugin's hook starts it and also watches the coordination issue named here, with a second watcher when that issue is in another repo. Every status, time or "still waiting" comes from a check in the same turn.

## Project rules
- 2026-11-10: More than 30 permission prompts in one session. Cause: `.claude/settings.local.json` set `defaultMode: acceptEdits`, overriding the user's auto mode. Fix: no `defaultMode` in repo files; shared rules live in `.claude/settings.json`.
- 2026-11-13: The map artifact still showed a merged PR as waiting for review. Causes: the rule only said to add new pieces, the artifact and `docs/MAP.md` were edited by hand separately, and the artifact copied PR status. Fix: check the whole map at fixed moments, build the artifact from `docs/MAP.md`, link live lists instead of copying status.
- 2026-11-14: After the human merged the TDD's PR, Claude still asked them to type "approved". Cause: a lesson about praise that came with open questions had been turned into "only the word 'approved' counts". Fix: a merge or a clear yes is approval. Get the yes before the merge, so the post-approval updates go into the same PR.
- 2026-11-15: Permission prompts mid-session again. Cause: Claude ran commands in the desktop Terminal panel, which asks the human every time, even in auto mode. Fix: never use the Terminal panel; run commands in Claude's own shell, with a script when a command must run from another folder.
- 2026-11-18: A PR that changed only docs still ran the full browser suite, about 25 minutes per push. Cause: apb#22 changed apb's playbook so docs-only pushes skip the browser tests, but nobody applied it to this repo's `ci.yml`, and the after-merge check didn't look here. Fix: when an apb change affects how projects run, make the matching change in this repo as soon as the apb PR merges, and after this repo's PR merges, check that it works here.
